## Замечания

**RA-01.** Элемент ТЗ: ФТ-19 (и ОВ-09). Категория: 2, 7 (противоречия; прослеживаемость).
Суть: ФТ-19 («при повреждении единица автоматически получает статус «в ремонте»») цитирует те же источники З-06 и З-09, что и ОВ-09, где прямо зафиксировано расхождение между З-06 (администратор вручную обновляет статус) и З-09 (переход в ремонт автоматический) — именно по вопросу перевода в ремонт. Но статус ФТ-19 — «Подтверждено», а не «Уточнить: ОВ-09», хотя формулировка ФТ-19 и есть предмет этого же противоречия.
Рекомендация: сменить статус ФТ-19 на «Уточнить: ОВ-09» либо явно развести зоны ответственности ФТ-19 (факт/причина перевода в ремонт) и ФТ-20 (последующие ручные изменения статуса, например после ремонта), обосновав, почему это не одно и то же противоречие.
Важность: высокая.

**RA-02.** Элемент ТЗ: ФТ-24 vs ДОП-04. Категория: 2 (противоречие требования и допущения).
Суть: ФТ-24 — «система учитывает штраф»; ДОП-04 — «начисление и применение штрафа выполняются вне системы». «Учитывает» можно прочитать как «рассчитывает/начисляет», что противоречит допущению о вынесении расчёта штрафа за пределы системы.
Рекомендация: привести формулировку ФТ-24 в соответствие с ДОП-04 (например: «система фиксирует факт и длительность просрочки для последующего начисления штрафа вне системы») либо, если предполагается расчёт штрафа внутри системы, снять ДОП-04 и явно вынести это в ОВ-04.
Важность: средняя.

**RA-03.** Элемент ТЗ: ФТ-02, ФТ-13, ФТ-15, ФТ-27. Категория: 1, 6 (требования слабо подтверждены интервью; недокументированные допущения).
Суть: конкретное поведение системы в этих пунктах не проговорено заказчиком дословно, а синтезировано из более общих реплик и представлено как «Подтверждено»: ФТ-02 (отказ регистрации при повторе серийного номера с сообщением об ошибке) собран из уникальности серийного номера (З-03) и общего правила обработки некорректного ввода (З-18); ФТ-15 (сверка отсканированной единицы с заявкой) опирается только на приёмочный критерий З-21, а не на явное функциональное описание; ФТ-13 («выдача только по подтверждённой заявке») и ФТ-27 («не сохраняет некорректные данные») — логические выводы из процесса, а не прямые цитаты.
Рекомендация: перенести эти пункты (или их спорную часть) в раздел 4.6 «Допущения» с обоснованием по аналогии с ДОП-01…ДОП-10, либо явно пометить как техническую интерпретацию исполнителя.
Важность: средняя.

**RA-04.** Элемент ТЗ: ФТ-05, ФТ-07. Категория: 3 (нет критериев приёмки).
Суть: оба требования подтверждены («Подтверждено») и однозначны, но ни в таблице КП, ни где-либо ещё нет ни одного критерия приёмки для них — при том что для парного ФТ-06 (импорт из HR-таблицы) критерий КП-14 есть.
Рекомендация: добавить, например: «Администратор вручную создаёт учётную запись сотрудника → запись появляется в списке с указанными данными и ролью»; «Администратор назначает пользователю роль ответственного лица → пользователь получает доступ к очереди заявок».
Важность: высокая.

**RA-05.** Элемент ТЗ: НФТ-02. Категория: 3.
Суть: базовое требование безопасности (вход по паролю) подтверждено, но не имеет отдельного критерия приёмки. КП-11 проверяет только разграничение доступа между уже вошедшими пользователями, а не сам вход/отказ по паролю.
Рекомендация: добавить критерий: «неверный пароль → доступ отклонён», «верный пароль → пользователь аутентифицирован под своей ролью».
Важность: высокая.

**RA-06.** Элемент ТЗ: ФТ-03, ФТ-04, ФТ-11, ФТ-12, ФТ-20, ФТ-23, ФТ-24, НФТ-04, НФТ-08. Категория: 3.
Суть: требования со статусом «Уточнить» (ожидают ответа на соответствующий ОВ) не имеют в таблице КП ни критерия, ни явной заглушки — хотя для аналогичного случая (ФТ-26, НФТ-05, НФТ-06) уже есть образцовая запись КП-15 «Требование не определено. Необходимо уточнение заказчика».
Рекомендация: по образцу КП-15 добавить для каждого перечисленного ID строку-заглушку со ссылкой на нужный ОВ — так полнота покрытия приёмки будет прослеживаема по всем ФТ/НФТ без пропусков.
Важность: средняя.

**RA-07.** Элемент ТЗ: п.4.1.1 (структура подсистем). Категория: 8, 7.
Суть: перечень подсистем в 4.1.1 покрывает ФТ-01…ФТ-26, ФТ-28, но не упоминает ФТ-27 (проверка и отклонение некорректных данных) ни в одной группе.
Рекомендация: включить ФТ-27 в подходящую подсистему («заявки» или отдельную сквозную группу «валидация данных»).
Важность: низкая.

**RA-08.** Элемент ТЗ: раздел 4.3 «Требования к видам обеспечения». Категория: 8.
Суть: ГОСТ 34.602-89 предполагает рассмотрение всех применимых видов обеспечения, а раздел раскрывает только информационное (4.3.1), техническое (4.3.2) и лингвистическое (4.3.3). По программному, организационному, методическому, правовому и математическому обеспечению нет ни содержания, ни явной пометки «не предъявлялось» (как сделано в 4.1.5 для эргономики и др.).
Рекомендация: добавить для остальных видов обеспечения формулировку по образцу 4.1.5 либо сослаться на уже имеющиеся ОГР-10/ВЗ-05 применительно к правовому обеспечению обработки ПДн.
Важность: средняя.

**RA-09.** Элемент ТЗ: ФТ-05 (источник З-13). Категория: 5, 6.
Суть: реплика З-13 — «Сотрудники добавляются в систему вручную администратором – обычно через импорт из HR-таблицы или ввод их данных в личный кабинет». Термин «личный кабинет» в остальных репликах закреплён за сотрудником (З-08), поэтому фраза может означать самостоятельный ввод данных сотрудником, что противоречило бы ОГР-09 («самостоятельная регистрация не предусмотрена»). ТЗ разрешило неоднозначность в пользу «администратор вводит вручную», не вынеся расхождение в ОВ.
Рекомендация: добавить открытый вопрос («кто физически вводит данные при ручном способе — администратор или сотрудник в своём личном кабинете?») либо зафиксировать выбранную трактовку как допущение с обоснованием в разделе 4.6.
Важность: низкая.

**RA-10.** Элемент ТЗ: ФТ-25 vs НФТ-03. Категория: 5, 6.
Суть: неясно, «история выдачи» (ФТ-25, по единице оборудования) и «журнал действий» (НФТ-03, по пользователям) — одна структура данных или две разные сущности. ОВ-23 спрашивает только про сроки хранения обеих, но не про их соотношение.
Рекомендация: уточнить у заказчика или зафиксировать допущение о структуре хранения (единый журнал с разными срезами или два независимых журнала) для модели данных в 4.3.1.
Важность: низкая.

**RA-11.** Элемент ТЗ: ФТ-21. Категория: 2, 4, 7.
Суть: ФТ-21 («отслеживает срок возврата по каждой выдаче и отмечает просроченные») помечен «Подтверждено», хотя срок использования по ФТ-08/ОВ-06 указывается «при необходимости», то есть может отсутствовать. Не определено, как трактовать «просрочку» для выдачи без срока — корректность формулировки ФТ-21 зависит от разрешения ОВ-06, что не отражено в его статусе.
Рекомендация: либо ограничить действие ФТ-21 только выдачами с указанным сроком, либо сменить статус на «Уточнить: ОВ-06».
Важность: средняя.
