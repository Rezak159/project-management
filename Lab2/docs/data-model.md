## 2. Решения, которые не видны на диаграмме

**Выдача не дублирует сотрудника и единицу.** Они берутся из заявки (`issue.request_id`, уникален: одна
заявка – не больше одной выдачи). Выдача без заявки невозможна (ФТ-13), поэтому расхождения между заявкой и
выдачей быть не может.

**История и журнал – разные таблицы.** История выдачи (`issue`, `unit_status_change`) хранится бессрочно
(ФТ-25), журнал действий (`audit_log`) – 1 год (НФТ-03). Если хранить всё в журнале, удаление старых записей
стёрло бы историю.

**Просрочка вычисляется, а не хранится.** Выдача просрочена, если `return_due_date` меньше текущей даты, а
`returned_at` пуст (ФТ-21). Бессрочная выдача (`return_due_date` пуст) просроченной не становится.
`overdue_days` накапливает дни просрочки по непересекающимся интервалам. Если продление согласовано, когда
срок уже прошёл, к полю прибавляются дни от старого срока до более ранней из двух дат – дня решения или
нового срока; при закрытии выдачи прибавляются дни после текущего срока. Пример: срок 2 ноября, решение
6 ноября, новый срок 4 ноября, возврат 6 ноября – при решении прибавляются 2 дня (2–4 ноября), при возврате
ещё 2 (4–6 ноября), итого 4. Так просрочка до продления не теряется и не считается дважды (ФТ-24, ФТ-26).

**Утеря закрывает выдачу (Д-11).** Перевод выданной единицы в «утерян» в одной транзакции закрывает её открытую
выдачу: `returned_at` – время отметки, `received_by_id` – кто отметил, `return_state = 'lost'`, накапливается
`overdue_days`. Единица перестаёт считаться на руках у сотрудника (лимит), письма по выдаче становятся
устаревшими, запрос продления на рассмотрении закрывается. Факт утери остаётся в истории и в справке ФТ-34.

**Запрос продления закрывается возвратом.** Запрос «на рассмотрении» по закрытой выдаче получает статус
`closed` при ближайшем запуске планировщика (SD-05): решать по возвращённой единице нечего. До этого
руководитель такой запрос решить не может – при решении проверяется, что выдача не закрыта. Руководитель берётся из `app_user.manager_id` на момент
решения, поэтому при смене руководителя ожидающий запрос переходит к новому (Д-14).

**Письмо проверяется перед отправкой.** `notification.due_date` хранит срок, от которого рассчитан `for_date`.
Перед каждой партией отправки модуль «Контроль сроков» отменяет (`cancelled`) письма, у которых выдача
закрыта, срок изменился или письмо `overdue` относится к прошедшему дню; такие письма не уходят (SD-05).
Если после смены срока письмо того же вида на тот же день снова нужно (выдача всё ещё просрочена), проверка
сроков не создаёт второе письмо, а возвращает неотправленное в очередь с новым сроком; отправленное письмо
не повторяется.

**Протокол загрузки из Excel не хранится отдельно.** Он показывается администратору после загрузки и
записывается в журнал (`audit_log.details`) (ФТ-06, ФТ-30).

## 3. Ограничения целостности

| № | Ограничение | Как обеспечивается | Требования |
|---|---|---|---|
| 1 | Серийный номер единицы уникален и соответствует формату Д-09 | Проверка формата в форме и при загрузке; уникальный индекс `equipment_unit.serial_number`; при нарушении – сообщение «Единица с таким серийным номером уже зарегистрирована» | ФТ-02, ОГР-01 |
| 2 | Табельный номер, e-mail и логин пользователя уникальны; названия подразделений и типов уникальны | Уникальные индексы; для e-mail – по `lower(email)`: на него приходит код входа, два пользователя с одним адресом получали бы чужие коды | ФТ-05, ФТ-06, НФТ-02 |
| 3 | Единица бронируется только из статуса «в наличии», даже если две заявки подтверждают одновременно | Бронирование одним условным запросом `UPDATE equipment_unit SET status = 'reserved' WHERE id = :id AND status = 'available'`; если изменено 0 строк – заявка отклоняется | ФТ-10, ФТ-12, ОГР-02, НФТ-08 |
| 4 | У единицы не больше одной подтверждённой заявки | Частичный уникальный индекс `request (unit_id) WHERE status = 'confirmed'` – страховка к п. 3 | ФТ-12 |
| 5 | Число единиц на руках не превышает лимит, даже при одновременных выдачах одному сотруднику | При выдаче строка сотрудника блокируется (`SELECT … FOR UPDATE`), затем считаются его незакрытые выдачи; выдача выполняется, только если их меньше лимита. Лимит можно снизить ниже числа единиц на руках – тогда новые выдачи невозможны, пока сотрудник не вернёт лишнее (Д-13) | ФТ-16, ФТ-32, ОГР-03 |
| 5а | Заявка меняет статус только из допустимого, даже при одновременных выдаче, отмене, подтверждении и истечении | Отмена, отклонение и исполнение – условный `UPDATE request … WHERE status IN (…)`; подтверждение, выдача и истечение сначала блокируют заявку `SELECT … FOR UPDATE` и проверяют статус и дату начала одной функцией модуля «Заявки». Истечение снимает бронь по статусу, прочитанному под блокировкой: заявка, подтверждённая перед полуночью, не остаётся «истекла» с забронированной единицей. Порядок блокировок во всех операциях: заявка → сотрудник → единица | ФТ-09…ФТ-13, ФТ-33, НФТ-08 |
| 5б | Выдача закрывается один раз | Возврат и утеря блокируют выдачу `SELECT … FROM issue WHERE id = :id AND returned_at IS NULL FOR UPDATE`; 0 строк – операция отклоняется, отметка и статус единицы не меняются | ФТ-18, ФТ-19, ФТ-25 |
| 6 | Статус единицы меняется только по таблице переходов | Все смены статуса – через одну функцию модуля «Учёт оборудования», которая проверяет переход и в той же транзакции пишет `unit_status_change` | ФТ-03, ОГР-08, policies.md П-02 |
| 7 | При отметке «повреждена» есть описание повреждения | Проверка `return_state <> 'damaged' OR damage_description <> ''` | ФТ-18 |
| 7а | Руководитель есть у каждого, кому можно выдать оборудование | Проверка `manager_id IS NOT NULL OR item_limit = 0`: без руководителя некому решать продление и получать письмо о просрочке (Д-14) | ФТ-23, ФТ-24 |
| 8 | Дата поверки задаётся только для измерительных приборов | Проверка при сохранении единицы по `equipment_type.is_measuring` | ФТ-01, ФТ-31 |
| 9 | Срок возврата не раньше даты начала; новый срок при продлении позже текущего; лимит не отрицательный; сотрудник не руководитель самому себе | Проверки (CHECK) и проверка форм | ФТ-08, ФТ-23, ФТ-27, ФТ-32 |
| 10 | По выдаче не больше одного запроса продления на рассмотрении | Частичный уникальный индекс `extension_request (issue_id) WHERE status = 'pending'` | ФТ-23 |
| 11 | Повторная проверка сроков не создаёт второе письмо за тот же день | Уникальный индекс `notification (issue_id, kind, for_date)`; `for_date` – срок минус N для `due_soon`, день после срока для `manager_overdue`, текущий день для `overdue`. При конфликте неотправленное письмо со старым сроком получает новый `due_date`, статус `pending` и сброшенный счётчик попыток (`ON CONFLICT … DO UPDATE … WHERE status <> 'sent'`), отправленное не меняется. Неотправленное письмо остаётся `pending` и повторяется каждые 15 минут, после 5 отказов сервера – `failed`; администратор возвращает его в очередь. Доставка – не менее одного раза: при сбое между приёмом письма сервером и записью `sent` письмо уйдёт повторно (ADR-005) | ФТ-22, ФТ-24 |
| 12 | Записи истории не удаляются | Внешние ключи с `ON DELETE RESTRICT`; пользователь не удаляется, а отключается (`is_active`); единица выводится из учёта статусом «списан» или «утерян» | ФТ-25 |
| 13 | Журнал хранится не меньше 1 года | Ежедневное удаление записей `audit_log` старше `audit_retention_days`; по умолчанию 365, форма настроек не принимает значение меньше 365 | НФТ-03 |
| 14 | Пароль и код входа не хранятся в открытом виде; после 6 неудачных попыток вход блокируется на 5 минут | `password_hash`, `code_hash`; код действует 10 минут и один раз: гасится в той же транзакции, где проверяется (`SELECT … FOR UPDATE`), новый код гасит прежние; счётчик увеличивается одним `UPDATE … SET failed_logins = failed_logins + 1`; на 6-й попытке тот же `UPDATE` ставит `locked_until` и обнуляет счётчик – следующая серия начинается после блокировки; успешный вход обнуляет счётчик; `locked_until` проверяется на шагах пароля и кода, каждый шаг – под блокировкой строки пользователя `SELECT … FOR UPDATE`, поэтому одновременные попытки не обходят блокировку | НФТ-02 |
| 15 | Персональные данные видят только администратор и право «управление пользователями» | Табельный номер, должность, e-mail и руководитель выдаются только этим ролям, остальным – ФИО и подразделение | НФТ-04 |
| 16 | Пароль почтового ящика не хранится в базе в открытом виде | Значение `smtp_password` в `setting` шифруется ключом, который задаётся на сервере вне базы данных; копия ключа хранится отдельно от копий базы (ADR-002) | ФТ-22, ВЗ-04 |

## 4. Проверка: хватает ли данных для сценариев

| Сценарий | Какие данные нужны | Где хранятся |
|---|---|---|
| Подача и рассмотрение заявки (BP-01, UC-02…UC-06) | Единицы «в наличии», заявка, кто её взял | `equipment_unit.status`, `request`, `request.reviewer_id` |
| Истечение и отмена заявки (ФТ-11, ФТ-33) | Дата начала, статус заявки, бронь единицы | `request.start_date`, `request.status`, `equipment_unit.status` |
| Выдача (BP-01, UC-07) | Единица из заявки, лимит, число единиц на руках, кто выдал | `request.unit_id`, `app_user.item_limit`, `issue` без `returned_at`, `issue.issued_by_id` |
| Пометка поверки (ФТ-31) | Дата следующей поверки | `equipment_unit.next_check_date` сравнивается с текущей датой |
| Возврат (BP-02, UC-08) | Открытая выдача единицы, состояние, описание повреждения | `issue`, `return_state`, `damage_description` |
| Ремонт, списание, утеря (UC-10) | Переходы статуса и кто их выполнил; при утере выданной единицы – её выдача | `unit_status_change`, `issue.return_state = 'lost'` |
| Напоминания и просрочка (BP-03, UC-21) | Срок возврата, e-mail сотрудника и руководителя, отправленные письма, число дней из справочника | `issue.return_due_date`, `app_user.email`, `app_user.manager_id`, `notification`, `setting.reminder_days`, `work_schedule` |
| Продление (UC-18, UC-19) | Новая дата и решение руководителя | `extension_request` |
| История единицы (ФТ-25, UC-22) | Все выдачи единицы: сотрудник, даты, кто выдал и принял, состояние | `issue` + `request` по `unit_id` |
| Отчёт «Остатки на складе» (ФТ-26) | Число единиц по типам и статусам | `equipment_unit` + `equipment_type` |
| Отчёт «Выдачи по сотрудникам» (ФТ-26) | Сколько единиц и сколько дней занимал сотрудник за период | `issue.issued_at`, `issue.returned_at` + `request.employee_id`; учитываются выдачи, пересекающие период, дни – календарные даты внутри периода, для незакрытой выдачи – по сегодня (Д-12) |
| Отчёт «Невозвращённое оборудование» (ФТ-26) | Сотрудник, единица, срок, длительность просрочки | Все незакрытые `issue`; длительность просрочки – `overdue_days` плюс дни после текущего срока, если он прошёл. Если текущий срок не прошёл, выводится только `overdue_days`: например, срок 2 ноября, 6 ноября продление до 10 ноября – отчёт 7 ноября показывает 4 дня. Без просрочки – 0, для бессрочной – «без срока» |
| Справка по сотруднику (ФТ-34, UC-24) | Взятые, возвращённые, находящиеся на руках единицы и отправленные в починку с описанием | `request`, `issue` по `employee_id`, `damage_description`, `equipment_unit.status = 'repair'` |
| Вход (UC-01) | Логин, хеш пароля, код из письма, неудачные попытки | `app_user`, `login_code` |
| Актуальность письма | Состояние выдачи и срок, от которого рассчитано письмо | `issue.returned_at`, `issue.return_due_date`, `notification.due_date` |
| Журнал (UC-25) | Кто, когда и что сделал | `audit_log` |
