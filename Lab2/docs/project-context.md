# Контекст проекта АС УВО

Автоматизированная система учёта выдачи и возврата оборудования сотрудникам (АС УВО), вариант 23.
Требования – техническое задание ЛР № 1: [ТЗ_вариант23.pdf](../../Lab1/ТЗ_вариант23.pdf), текстовая копия
с теми же идентификаторами – [requirements.md](requirements.md). Ниже требования указываются только
идентификаторами.

## 1. Назначение и границы автоматизации

Система ведёт поштучный учёт оборудования организации (ручной инструмент, измерительные приборы, небольшая
техника), заявки сотрудников на оборудование, выдачу и возврат, контроль сроков возврата, историю выдачи
и отчёты (ОГР-01, ФТ-01…ФТ-34).

| В системе | Вне системы |
|---|---|
| Статус каждой единицы и его переходы (ФТ-03) | Ремонт, списание и поиск утерянного оборудования – система хранит только статус (ОГР-12) |
| Заявки, их рассмотрение и выдача по заявке (ФТ-08…ФТ-17) | Увольнение сотрудника – система выдаёт справку (ОГР-12, ФТ-34) |
| Отметка о состоянии при возврате (ФТ-18) | Назначение штрафа за просрочку (ОГР-06, ФТ-24) |
| Напоминания и уведомления по e-mail (ФТ-22, ФТ-24) | Поверка приборов – система хранит дату и ставит пометку (ФТ-31) |
| Загрузка данных из Excel и выгрузка отчётов в Excel (ФТ-06, ФТ-26, ФТ-30) | Закрепление ответственных лиц за видами оборудования (ОГР-13) |

Не реализуются: шифрование базы данных и ограничение доступа по IP-адресам (ОГР-14).

## 2. Пользователи и внешние системы

| Роль | Что делает в системе | Требования |
|---|---|---|
| Сотрудник | Подаёт и отменяет заявки, видит свои заявки, запрашивает продление срока | ФТ-08, ФТ-23, ФТ-28, ФТ-33 |
| Ответственное лицо | Берёт заявку из общей очереди, подтверждает или отклоняет её | ФТ-09, ФТ-10, ФТ-12 |
| Заведующий складом | Выдаёт и принимает оборудование, отмечает состояние, меняет статусы «починка», «списан», «утерян» | ФТ-13…ФТ-20 |
| Руководитель | Согласует продление срока, видит просроченные выдачи своих сотрудников | ФТ-23, ФТ-24 |
| Администратор | Ведёт каталог, справочники, учётные записи, роли и лимиты, формирует отчёты | ФТ-01, ФТ-04…ФТ-07, ФТ-26, ФТ-30, ФТ-32, ФТ-34 |
| Пользователь с правом «управление пользователями» | Создаёт учётные записи, видит полные данные сотрудников | ФТ-05, НФТ-04 |

Каждый пользователь – сотрудник организации; остальные роли добавляются к роли «Сотрудник», один
пользователь может совмещать роли (ФТ-07). Самостоятельной регистрации нет (ОГР-09).

Внешние подключения ограничены перечнем ОГР-11:

| Внешняя система или устройство | Для чего | Требования |
|---|---|---|
| Почтовый сервер заказчика (SMTP) | Одноразовый код входа, напоминания сотруднику, письмо руководителю о просрочке | НФТ-02, ФТ-22, ФТ-24, ВЗ-04 |
| USB-сканер штрихкодов | Определение единицы при выдаче и возврате | ФТ-14, ВЗ-01 |
| Принтер | Печать этикеток со штрихкодом Code 128 | ФТ-29, ВЗ-02 |
| Файлы Excel (.xlsx) | Загрузка каталога и сотрудников, выгрузка отчётов | ФТ-06, ФТ-26, ФТ-30, ВЗ-03 |

## 3. Основные функции

| Подсистема (ТЗ, п. 4.1) | Функции | Требования |
|---|---|---|
| Учёт оборудования | Регистрация единицы, штрихкод и этикетка, загрузка каталога, статусы, пометка поверки, справочники | ФТ-01…ФТ-04, ФТ-20, ФТ-29…ФТ-31 |
| Пользователи и роли | Учётные записи, загрузка сотрудников, роли, лимиты, вход | ФТ-05…ФТ-07, ФТ-32, НФТ-02 |
| Заявки | Подача, общая очередь, рассмотрение, отмена, истечение | ФТ-08…ФТ-12, ФТ-28, ФТ-33 |
| Выдача и возврат | Выдача по подтверждённой заявке, проверка единицы и лимита, приём с осмотром | ФТ-13…ФТ-19 |
| Контроль сроков | Просрочка, напоминания, продление, уведомление руководителя | ФТ-21…ФТ-24 |
| История и отчёты | История единицы, три отчёта, справка по сотруднику | ФТ-25, ФТ-26, ФТ-34 |

Проверка вводимых данных (ФТ-27) и журнал действий (НФТ-03) относятся ко всем подсистемам.

## 4. Требования, влияющие на архитектуру

| Требование | Влияние на архитектуру | Где решено |
|---|---|---|
| НФТ-09 | Веб-клиент в браузере; для установки как PWA нужны манифест, service worker и HTTPS | ADR-003, architecture.md |
| НФТ-05, НФТ-08 | Одновременная работа всех сотрудников с ответом до 10 с | ADR-001, ADR-002 |
| НФТ-06, НФТ-07 | Завершённая операция фиксируется в СУБД до ответа пользователю; резервное копирование и восстановление не дольше 24 ч | ADR-002, architecture.md |
| НФТ-01, НФТ-04 | Проверка роли и прав на сервере при каждом запросе; полные персональные данные – только администратору и праву «управление пользователями» | architecture.md, policies.md |
| НФТ-02 | Вход зависит от доставки кода через почтовый сервер заказчика | ADR-005, architecture.md |
| НФТ-03, ФТ-25 | Журнал действий хранится 1 год, история выдачи – бессрочно: две разные структуры хранения | data-model.md |
| ФТ-11, ФТ-21, ФТ-22, ФТ-24 | Действия по наступлению даты без участия пользователя – нужен запуск по расписанию | ADR-005 |
| ФТ-12, ОГР-02, НФТ-08 | Два ответственных лица могут одновременно подтверждать заявки на одну единицу – бронирование должно быть атомарным | data-model.md, sequence-request-review.puml |
| ФТ-14 | Сканер работает с веб-страницей без драйвера; ручной ввод – тот же сценарий | ADR-004 |
| ФТ-04 | Справочники и сроки напоминаний хранятся в базе данных, а не в коде | data-model.md, policies.md |
| ОГР-11 | Других интеграций (учётные системы, каталог пользователей) нет | architecture.md |

## 5. Допущения

Решения исполнителя там, где ТЗ сведений не даёт. Каждое допущение используется в указанных материалах.

| ID | Допущение | Основание | Где используется |
|---|---|---|---|
| Д-01 | Система разворачивается на сервере заказчика в его сети | ОГР-11 (единственное внешнее подключение – почтовый ящик), НФТ-04 | architecture.md, ADR-001 |
| Д-02 | Сканер работает в режиме эмуляции клавиатуры (HID): передаёт код как набранный текст и нажатие Enter | Стандартный режим USB-сканеров (ВЗ-01) | ADR-004 |
| Д-03 | Этикетка печатается из браузера на принтер, установленный в операционной системе | ФТ-29, ВЗ-02 | architecture.md |
| Д-04 | «Конец дня» в ФТ-11 и ФТ-21 – 24:00 по часовому поясу сервера. Письма отправляются в рабочие часы по графику; письмо, день которого пришёлся на нерабочий день, уходит в первый рабочий день. «Ежедневно» в ФТ-22 – каждый рабочий день | ФТ-11, ФТ-21, ФТ-22, НФТ-06 | ADR-005, sequence-deadlines.puml |
| Д-05 | Роль «Сотрудник» есть у каждого пользователя | ФТ-05, ФТ-07 | use-cases.md, data-model.md |
| Д-06 | Число сотрудников заказчика – до 1000; все могут работать одновременно | НФТ-08: число одновременных пользователей равно числу сотрудников; оборудование выдаёт один склад (ФТ-13) | ADR-001, ADR-002 |
| Д-07 | При отказе сервера допускается потеря изменений не более чем за 15 минут: кроме ежедневной резервной копии базы данных непрерывно архивируется журнал транзакций | НФТ-06 задаёт только время восстановления; потеря дня выдач лишила бы учёт смысла (цели ТЗ, раздел 2) | ADR-002, architecture.md |
| Д-08 | Сертификат HTTPS для имени сервера выпускает заказчик (свой удостоверяющий центр или публичный сертификат); браузеры сотрудников ему доверяют | НФТ-09: PWA устанавливается только с доверенным HTTPS | architecture.md, ADR-003 |
| Д-09 | Серийный номер – от 1 до 40 символов: латинские буквы, цифры, «-», «/», «.»; хранится в верхнем регистре. Табельный номер – от 1 до 20 цифр | ФТ-27 требует проверять формат, но формат в ТЗ не задан; Code 128 кодирует такие символы (ФТ-29) | ADR-004, data-model.md, policies.md |

## 6. Риски

| ID | Риск | Как учитывается |
|---|---|---|
| Р-01 | Почтовый сервер заказчика недоступен – одноразовый код не приходит, новый вход невозможен (НФТ-02) | Сессия действует до конца рабочего дня, поэтому вошедшие пользователи продолжают работу; ошибка отправки кода записывается в журнал и показывается администратору. Обходной вход без кода не делается – это нарушило бы НФТ-02 |
| Р-02 | Сканер неисправен | Серийный номер вводится вручную в то же поле (ФТ-14, У-32) |
| Р-03 | Состояние при возврате оценивается субъективно | Отметка заведующего складом окончательная, ответственность на нём (ФТ-18, У-33) |
