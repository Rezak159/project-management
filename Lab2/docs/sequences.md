## SD-01 Вход в систему

Вход в два шага: пароль, затем одноразовый код из письма (НФТ-02). Неверный пароль и неверный код
считаются одной серией неудачных попыток: на 6-й подряд вход блокируется на 5 минут, успешный вход
сбрасывает счётчик. Код действует 10 минут и один раз, в базе хранится только его хеш (data-model.md, п. 14).

Код отправляется сразу, а не через очередь писем: пользователь ждёт его на экране. Если почтовый сервер
недоступен, вход невозможен, ошибка записывается в журнал. Обходного входа без кода нет, а сессия
действует до конца рабочего дня, поэтому вошедшие пользователи продолжают работу (Р-01, ADR-005).

## SD-02 Рассмотрение заявок на одну единицу

Показан случай из ФТ-12: две заявки на одну единицу рассматривают два ответственных лица одновременно.

- Взять заявку можно только свободную – условие `reviewer_id IS NULL` в том же запросе, который её
  закрепляет (ФТ-09, ОГР-04). Если два человека нажали «Взять» одновременно, заявку получает один.
- Подтверждение бронирует единицу условным запросом `… WHERE status = 'available'`. СУБД блокирует строку
  единицы, поэтому вторая транзакция ждёт первую и после её фиксации изменяет 0 строк. Вторая заявка
  отклоняется системой с причиной «единица не в наличии» (ФТ-10, ФТ-12, data-model.md, п. 3).
- Смена статуса единицы идёт через модуль «Учёт оборудования», который пишет историю статусов (П-02,
  policies.md).

## SD-03 Выдача по заявке

Сканер работает как клавиатура: передаёт серийный номер в поле формы и нажимает Enter (Д-02, ADR-004).
Поэтому ручной ввод при неисправном сканере – то же поле и тот же запрос (ФТ-14).

Проверки по порядку: единица существует; это единица из заявки (ФТ-15); у сотрудника не достигнут лимит
(ФТ-16). Лимит проверяется в транзакции после блокировки строки сотрудника `SELECT … FOR UPDATE`: две
одновременные выдачи одному сотруднику не превысят лимит (data-model.md, п. 5). При успехе в одной
транзакции записываются выдача (ФТ-17), статус единицы «выдано», статус заявки «исполнена» (ФТ-13) и
запись журнала. Пометка о дате поверки показывается, но выдачу не запрещает (ФТ-31).

## SD-04 Приём возврата с повреждением

Система находит открытую выдачу по серийному номеру; если её нет, возврат не выполняется. Отметку
«повреждена» без описания система не сохраняет (ФТ-18, ФТ-27). Возврат, длительность просрочки (ФТ-24),
переход «выдано → починка» (ФТ-19) и запись журнала сохраняются в одной транзакции: после ответа «Возврат
принят» данные не теряются при сбое (НФТ-07).

## SD-05 Ежедневная обработка сроков

Планировщик – отдельный процесс, который каждые 15 минут вызывает функции модулей (ADR-005):

- при первом запуске после 00:00 по часовому поясу сервера заявки, не выданные до конца даты начала,
  получают статус «истекла»,
  бронь снимается (ФТ-11, Д-04). Каждая заявка – отдельная транзакция, ошибка по одной не мешает
  остальным;
- в рабочие часы модуль «Контроль сроков» ставит письма в очередь: за N дней до срока (ФТ-22, ФТ-04),
  в первый день просрочки руководителю (ФТ-24), каждый рабочий день просрочки сотруднику (ФТ-22).
  Бессрочные выдачи не выбираются (ФТ-21). День письма хранится в `for_date`: для напоминания о сроке –
  срок минус N, для письма руководителю – день после срока. Поэтому письмо, день которого пришёлся на
  выходной, уходит в первый рабочий день, но только один раз (Д-04);
- модуль «Уведомления» отправляет письма из очереди. Если почтовый сервер недоступен, письмо остаётся в
  очереди и отправляется при следующем запуске; после 5 неудачных попыток – статус «не отправлено»,
  ошибка видна администратору в журнале.

Письмо в очереди уникально по выдаче, виду и дню (data-model.md, п. 11), поэтому повторный запуск проверки,
например после перезапуска сервера, не рассылает письма второй раз.
